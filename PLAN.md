# Instagram Clone — Plan & Roadmap (v1)

## 1. Key decisions

### Auth: server-side sessions + httpOnly cookie (browser-only for now)
- On login: verify the password (**argon2id**), generate a random session ID (32+ bytes), store its
  **SHA-256 hash** in `sessions`, and send the raw ID as a cookie:
  `sid=<id>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000`
- Every request: hash the cookie → look up the session → load the user (`req.user`).
- Logout: delete the row and clear the cookie. "Log out all devices": delete all of the user's rows.
- **Always create a new session on login** (prevents session fixation).
- **Expiry**: 30-day idle timeout (sliding, via `last_seen_at`; update it at most once per hour to avoid a write on every request) + 90-day absolute maximum.
- Why not JWT: JavaScript can't read an httpOnly cookie (XSS can't steal it), revocation is instant, and the frontend needs no token handling. The cost is one indexed DB lookup per request → Redis later).
- If mobile clients are added later, token auth can be added alongside sessions.

### CSRF protection
Cookies are sent automatically, so other sites could try to trigger actions as the user. Layers:
1. `SameSite=Lax` cookie: not sent on cross-site POST/PUT/PATCH/DELETE.
2. **Never change state on GET** (Lax still sends cookies on top-level GET navigations).
3. Mutating requests must be `Content-Type: application/json` (HTML forms can't send JSON), otherwise 415.
4. Mutating requests must have an `Origin` header matching `FRONTEND_ORIGIN`, otherwise 403.

No CSRF tokens for now. Add them only if you need very old browsers, or if you ever serve untrusted
content from a subdomain of the app's domain (SameSite treats subdomains as same-site).

### Frontend ↔ API: same origin via Next.js rewrites
- `next.config.ts` proxies `/api/*` → Fastify API (`API_URL`). The browser only sees the Next.js origin.
- Session cookie is first-party, **no CORS** and no `credentials: "include"` needed.
- Server components can read the cookie and forward it to the API for server-rendered pages.
- `proxy.ts` can redirect to `/login` when the cookie is missing (an optimistic check; the API still does
  the real one).
- The API sits behind a proxy: enable Fastify `trustProxy` so `req.ip` comes from `X-Forwarded-For`.

### Database: PostgreSQL
- The data is relational: users ↔ posts ↔ media, and soon follows, likes, comments, feeds.
- DynamoDB means designing every access pattern in advance (single-table design). That's hard
  while the product keeps changing. Postgres lets you add queries and indexes as you go.
- Postgres scales well past what this app will need (indexes, read replicas, partitioning), and
  Redis in front of it later takes care of hot reads.
- Hosting: Docker locally → RDS / Neon / Supabase in production.

### Media: S3 + presigned URLs + multipart upload
- The bucket is **private**. Clients upload **directly to S3**, so file bytes never pass through the API.
- **Multipart** for videos and large files (part size 5–10 MB; S3 minimum is 5 MB except for the
  last part; max 10,000 parts). For images under ~10 MB, a **single presigned PUT** is simpler
  (optional: you can use multipart for everything to keep one code path).
- S3 keys are generated by the server and never taken from the client: `users/{userId}/media/{uuid}.{ext}`.
- Reads: short-lived presigned GET URLs for now → CloudFront later.

## 3. Data model (v1)
```sql
users           (id uuid pk, email citext unique, username citext unique, password_hash,
                 display_name, bio, avatar_media_id, created_at, updated_at)

sessions        (id uuid pk, user_id fk, token_hash unique, created_at, last_seen_at,
                 expires_at, user_agent, ip)

media           (id uuid pk, owner_id fk, s3_key unique, type enum('image','video'),
                 content_type, size_bytes, status enum('pending','uploaded','failed'),
                 s3_upload_id null, width, height, duration_ms, created_at)

posts           (id uuid pk, author_id fk, caption text, created_at, updated_at, deleted_at)

post_media      (post_id fk, media_id fk unique, position smallint, pk(post_id, position))
```
Indexes: `posts(author_id, created_at desc)`, `media(owner_id, status)`, `sessions(user_id)`.

## 4. API (v1)
The browser calls these as `/api/...` (Next.js rewrites strip the prefix and forward to the API).

### Auth
```
POST   /auth/register        { email, username, password } → { user } + session cookie
POST   /auth/login           { emailOrUsername, password } → { user } + session cookie
POST   /auth/logout          delete current session, clear cookie
POST   /auth/logout-all      delete all of the user's sessions
GET    /me                   current user (401 if no valid session)
```

### Uploads (multipart flow)
```
POST   /uploads                          { contentType, sizeBytes, type }
         → validate type/size limits, create media(status=pending),
           CreateMultipartUpload → { mediaId, uploadId, key, partSize, partCount }

POST   /uploads/:mediaId/parts           { partNumbers: [1..n] }
         → { urls: [{ partNumber, url }] }   (presigned UploadPart, ~15 min expiry, batch)

POST   /uploads/:mediaId/complete        { parts: [{ partNumber, etag }] }
         → CompleteMultipartUpload → HeadObject (check size/content-type) → status=uploaded

DELETE /uploads/:mediaId                 → AbortMultipartUpload, status=failed
```
Client: split file → PUT each part to its URL (3–4 in parallel, retry failed parts) → collect
`ETag` response headers → call `complete`.

### Posts
```
POST   /posts                { caption, mediaIds: [...] }   (1–10 media, owned by user, status=uploaded, not already attached)
GET    /posts/:id
GET    /users/:username/posts?cursor=...&limit=20    (cursor pagination on created_at,id)
PATCH  /posts/:id            { caption }
DELETE /posts/:id            (soft delete)
```

## 5. S3 gotchas to handle early
- **Bucket CORS** must allow `PUT` from your frontend origin and **`ExposeHeaders: ["ETag"]`**,
  or the browser can't read part ETags.
- **Lifecycle rule**: abort incomplete multipart uploads after 1 day (otherwise you pay for orphaned parts).
- Clean up `pending` media rows older than 24h (a cron job for now, a queue worker later).
- Enforce limits on the server (e.g. images ≤ 20 MB, videos ≤ 500 MB, allowed MIME types) and verify
  with `HeadObject` on complete. Don't trust client-reported values.
- The IAM user/role for the API gets only `s3:PutObject`, `s3:GetObject`, `s3:AbortMultipartUpload`,
  `s3:ListMultipartUploadParts` on this bucket.

- [x] Git repo at the root (`fe/` + `be/` + plan)

### Phase 1: Auth (≈ 3–5 days)
- [ ] `users`, `sessions` tables
- [ ] register / login / logout / logout-all / me
- [ ] Auth hook (session cookie → `req.user`), idle + absolute expiry
- [ ] CSRF hook: JSON-only + `Origin` check on mutating requests

- [ ] Frontend: login page ✅, signup page, `proxy.ts` redirect for logged-out users
- [ ] Tests: happy paths, wrong password, expired session, CSRF rejections (wrong Origin, form content type)

### Phase 2: Media uploads (≈ 4–6 days)

- [ ] `posts`, `post_media` tables
- [ ] create (in a transaction, validating media ownership/status), get, list by user (cursor), edit caption, delete

### Phase 4: Hardening & deploy (≈ 3–5 days)

## 7. Later (don't build yet, but design with these in mind)
- **Social graph**: follows, likes, comments, profile pages
- **Feed**: start with "pull" (query posts of followed users); move to fan-out-on-write + Redis
  when it gets slow
- **Queue (SQS/BullMQ)**: S3 `ObjectCreated` event → worker for image resizing (sharp), video
  transcoding (MediaConvert/ffmpeg → HLS), thumbnails, EXIF stripping, content moderation. Media gets new
  statuses: `processing` → `ready`.
- **Redis**: session store, feed cache, counters (likes/followers), distributed rate limiting
- **Mobile clients**: add token auth (short-lived JWT access + rotating refresh tokens) next to sessions
- **CloudFront** with signed URLs/cookies for media delivery
- Notifications, search (Postgres full-text → OpenSearch), stories, DMs
