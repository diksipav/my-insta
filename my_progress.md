- **25.09.2026** I developed a stronger understanding of TLS termination. Most managed hosting platforms terminate HTTPS at an edge server, load balancer, or reverse proxy before forwarding the request to the backend application. The proxy typically preserves information about the original client request through headers such as X-Forwarded-For (client IP) and X-Forwarded-Proto (original protocol). A request may pass through multiple proxies, so before deployment I need to check my hosting provider’s proxy topology and configure Express’s trust proxy setting accordingly. Rate limiting can happen in Cloudflare (or load balancer/proxy) - IP rate limiting, and it can happen on the server (express rate-limit middleware) - limit by userId etc. Wow, there is so much to security, attackers can manipulate X-Forwarded-For and -Proto etc, can trick our server and bypass rate-limit...

- **26.09.2026** Password hashing should be intentionally slow so that, if attackers steal your database, they cannot test billions of password guesses cheaply. [OWASP - Open Worldwide Application Security Project](https://owasp.org/) recommends [argon2id](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) which is deliberately both RAM and CPU expensive. `Argon2id` is the current standard (wins over scrypt and bcrypt). Salt is public and saved in DB with rest of the hash. Its job is to ensure that every user has a different hash, even if they choose the same password. Pepper is secret and is stored in separate secret vaults.

- **27.09.2026** `SameSite` is a cookie setting that tells the browser when it may attach that cookie to a request that began from another site. It helps reduce `CSRF` (Cross-site request forgery) risk. `Lax` vs `Strict`. With `Lax`, a user can click a link from another site to your app and still arrive logged in. Cookie only attached to `GET` requests in this case.
